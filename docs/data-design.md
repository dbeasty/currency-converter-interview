## Tables

### `transactions`

Stores the raw purchase record in USD as submitted by the client. This is the source-of-truth for the original transaction and is never mutated after creation.

| Column | Type | Nullable | Notes |
|--------|------|----------|-------|
| `id` | `UUID` | NO | Primary key, generated by the application |
| `description` | `VARCHAR(50)` | NO | Human-readable label for the purchase |
| `transaction_date` | `DATE` | NO | Calendar date of the purchase; must not be in the future |
| `amount_usd` | `DECIMAL(19,2)` | NO | Purchase amount in US dollars, rounded to 2 d.p. |
| `created_at` | `TIMESTAMP` | YES | Set to `CURRENT_TIMESTAMP` on insert; UTC |

**Note on "must not be in the future":** The "today" boundary used to validate `transaction_date`
is defined by the application's business timezone (`app.treasury.timezone`, ET by default) via a
Spring `Clock` bean. This prevents servers running in other timezones (e.g. PST) from changing
edge-case validation behavior near midnight.

---

### `exchange_rates`

A local cache of rates fetched from the Treasury Fiscal Data API. Each row represents a unique `(currency, effective_date)` pair. Rows are upserted (not duplicated) whenever a new rate is fetched.

| Column | Type | Nullable | Notes |
|--------|------|----------|-------|
| `id` | `UUID` | NO | Primary key |
| `currency` | `VARCHAR(255)` | NO | Treasury `country_currency_desc` value (e.g. `Canada-Dollar`) |
| `rate` | `DECIMAL(19,6)` | NO | Exchange rate relative to USD |
| `effective_date` | `DATE` | NO | Date the rate became authoritative (used for filtering — see [java-app.md](java-app.md#treasury-rate-selection)) |
| `source_timestamp` | `TIMESTAMP` | YES | When the row was last fetched from Treasury; UTC |

**Unique constraint:** `(currency, effective_date)` — prevents duplicate rates for the same currency and date.

---

### `conversion_records`

An immutable audit log. Every time a `GET /transactions/{id}` call successfully produces a converted amount, a new row is written here.

**Why store the rate on the conversion row?**  
`exchange_rates` is a living cache: rows are upserted when Treasury data is refreshed, and operational fixes could in principle change stored values. The conversion record therefore keeps a **point-in-time snapshot** of the rate and effective date that were actually applied (`exchange_rate_used`, `exchange_rate_effective_date`), plus a FK to `exchange_rates` for traceability. That gives a durable **history of what happened** for each conversion—reports, disputes, and replays can see the exact inputs that produced `converted_amount` without depending on the current state of the rate table.

| Column | Type | Nullable | Notes |
|--------|------|----------|-------|
| `id` | `UUID` | NO | Primary key |
| `transaction_id` | `UUID` | NO | FK → `transactions.id` |
| `exchange_rate_id` | `UUID` | NO | FK → `exchange_rates.id` |
| `exchange_rate_effective_date` | `DATE` | NO | Denormalised copy of the rate's effective date for fast audit queries |
| `exchange_rate_used` | `DECIMAL(19,6)` | NO | Snapshot of the rate at conversion time |
| `converted_amount` | `DECIMAL(19,2)` | NO | `amount_usd × exchange_rate_used`, rounded to 2 d.p. |
| `conversion_timestamp` | `TIMESTAMP` | YES | When the conversion was performed; UTC |

**Foreign keys:**
- `fk_conversion_transaction`: `conversion_records.transaction_id` → `transactions.id`
- `fk_conversion_exchange_rate`: `conversion_records.exchange_rate_id` → `exchange_rates.id`

## Type Decisions

| Concern | Choice | Reason |
|---------|--------|--------|
| Primary keys | `UUID` | Avoids sequential ID enumeration; safe to expose in URLs |
| Monetary amounts | `DECIMAL(19,2)` | Exact decimal arithmetic; no floating-point rounding errors |
| Exchange rates | `DECIMAL(19,6)` | Six decimal places matches Treasury API precision |
| Audit timestamps | `TIMESTAMP` (stored as UTC `Instant` in Java) | Unambiguous; no daylight-saving edge cases |
| Calendar dates | `DATE` (stored as `LocalDate` in Java) | Date-only semantics; timezone-free by design |

**Rule of thumb:** Use `LocalDate` for business/effective dates (purchase date, Treasury
`effective_date`). Use `Instant` for event/audit timestamps (row creation time, conversion time,
token issue/expiry). When comparing against "today" or "current month", use the Spring-provided
`Clock` (business timezone) rather than the JVM default timezone.

## Migrations

Schema is managed by **Liquibase**. Changesets run automatically on application startup.

| Changeset | File | Description |
|-----------|------|-------------|
| `001-create-transactions` | `001-create-transaction-table.yaml` | Creates `transactions` table |
| `002-create-conversions` | `002-create-conversion-table.yaml` | Creates `conversion_records` table + FKs |
| `003-create-exchange-rates` | `003-create-exchange-rate-table.yaml` | Creates `exchange_rates` table + unique constraint |
| `004-add-indexes` | `004-add-indexes.yaml` | Adds `idx_conversion_records_transaction_id` |

Changeset files live in `api/currencyconverter/src/main/resources/db/changelog/changes/`.
